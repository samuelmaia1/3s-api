1. Descrição do Software

A 3S API é um sistema de gestão empresarial desenvolvido para a empresa 3S Letreiros, especializada na produção e locação de letreiros e placas decorativas. A aplicação é uma API REST completa construída com Java 21 e Spring Boot 4.0.1, utilizando banco de dados PostgreSQL hospedado na nuvem (Neon), autenticação via JWT e comunicação em tempo real por WebSocket (STOMP).

O sistema centraliza as operações de negócio da empresa em um único back-end, expondo endpoints REST consumidos por um front-end web. As principais funcionalidades são:

  • Gestão de usuários: cadastro, autenticação com JWT + refresh token, atualização de perfil
  • Gestão de produtos: controle de estoque, preço, imagem e busca por nome
  • Gestão de clientes: cadastro com validação de CPF e e-mail únicos
  • Pedidos de venda: criação com itens, cálculo de total, controle de status e devolução de estoque no cancelamento
  • Aluguéis: reserva de produtos com validação de disponibilidade no período, taxa de entrega e múltiplos status
  • Contratos: geração de contratos em PDF com cláusulas customizáveis, assinatura e cancelamento
  • Recibos: geração de recibos em PDF para pedidos e aluguéis
  • Dashboard gerencial: métricas de aluguéis ativos, receita mensal e últimas transações
  • Notificações em tempo real: eventos publicados via WebSocket após cada operação crítica

A arquitetura segue o padrão de três camadas: Presentation (Controllers e DTOs), Domain (regras de negócio, entidades, serviços e políticas) e Infrastructure (persistência JPA, segurança, configurações).

4. Cálculo de Cobertura de Testes

4.1 Ferramenta Utilizada

A cobertura foi calculada automaticamente pela ferramenta JaCoCo 0.8.12 (Java Code Coverage), integrada ao projeto via plugin Maven. O relatório é gerado automaticamente ao executar o comando mvn test, sendo salvo em target/site/jacoco/ nos formatos HTML, XML e CSV.

4.2 Escopo da Medição

O escopo de medição foi restrito à camada de domínio do projeto. As camadas de infraestrutura (persistência JPA, segurança, configurações) e de apresentação (controllers REST, DTOs) foram excluídas por serem adaptadores técnicos que não contêm regras de negócio e requerem testes de integração com banco de dados real para serem validados adequadamente. Essa é uma prática padrão em arquiteturas que seguem os princípios de separação de responsabilidades.

5. Considerações Finais

5.1 Estratégia de Teste Adotada

A equipe adotou a estratégia de testes unitários com foco na camada de domínio, por ser a camada que concentra toda a lógica de negócio da aplicação e é independente de frameworks externos (banco de dados, HTTP, WebSocket). Isso permite que os testes sejam rápidos, determinísticos e fáceis de manter.

Para os serviços que possuem dependências externas (repositórios, template de mensagens), foi utilizado Mockito para criar objetos simulados (mocks), garantindo o isolamento da unidade testada. Essa técnica permite verificar não apenas o resultado das operações, mas também se as dependências foram chamadas corretamente (verificação de interações via verify()).

5.2 Tipos de Casos de Teste Implementados

  • Testes de valor válido (happy path): verificam o comportamento correto quando os dados de entrada são válidos
  • Testes de valor inválido: verificam se exceções são lançadas com dados inválidos (ex.: CPF com menos de 11 dígitos, quantidade de item igual a zero)
  • Testes de valor limite: verificam comportamento nos limites (ex.: quantidade exatamente igual ao estoque disponível)
  • Testes de estado: verificam transições de estado das entidades (ex.: contrato cancelado não pode ser assinado)
  • Testes de interação: verificam se os colaboradores (repositórios, serviços) foram invocados com os parâmetros corretos
  • Testes de nulidade: verificam comportamento com valores nulos (ex.: cálculo de subtotal com valor unitário nulo)

5.5 Conclusão

O trabalho demonstrou a importância e a viabilidade de se obter alta cobertura de testes em sistemas reais de médio porte. Com 169 casos de teste e cobertura de 71,06% das linhas de código da camada de domínio, superou-se o requisito mínimo de 70% estabelecido para o trabalho. A adoção de ferramentas automatizadas como JaCoCo elimina subjetividade no cálculo da cobertura e fornece relatórios detalhados que facilitam a identificação de áreas de risco não testadas.
